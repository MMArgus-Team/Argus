# 序章：一个会看、会听、会想、会说的 Agent

> "The eye sees only what the mind is prepared to comprehend."
> —— Henri Bergson

## 从"打字问答"到"边看边聊"

2023 年，大多数人与 AI 的交互方式是这样的：打开一个对话框，敲一段文字，等它回一段文字。你说一句，它答一句，像在给一个博学但被关在暗室里的朋友发短信——他知识渊博，却看不见你的屏幕、��不到你的声音、也���不住三天前你们聊过什么。

Argus 想做的，是把这位朋友从暗室里放出来。

给他一双眼睛，让他看见你的摄像头、你正在共享的屏幕、你正在播放的视频；给他一对耳朵，让他听见你说话、也听见画面里的人在说什么；给他一颗会持续运转的大脑，让他即使你不发问也在默默观察、记忆、推理；再给他一张嘴，让他能像朋友那样开口回你话——不是冷冰冰地念答案，而是带着语气、会被你打断、会主动关心你。

这四件事，就是本书要讲的四个层面：**看、听、想、说**。

它们不是四个孤立的模块，而是一套围绕**一条永远在流动的视频/音频流**协同工作的活系统。理解 Argus，关键不在于任何单个组件写得多巧妙，而在于理解这四层如何共享同一份感知、如何分工、如何在"实时"与"深度"这对天然矛盾之间做取舍。

> **本书写给谁：** 想看懂 Argus 多模态子系统的工程师、想借鉴"实时多模态 Agent"设计的架构师，以及对"AI 如何在连续感知下工作"感兴趣的读者。每一章都尽量做到：先讲清楚**为什么**这么设计，再落到**代码在哪、怎么写的**。

## 一句话概括这套系统

Argus 是一个能"边看边聊"的多模态助手。它的主 Agent 处理**用户文本与语义路由**，不被动接收当前画面；一次性视觉问题和"持续盯着视频流"的重活都交给专职 worker。用项目 README 里的话说，多模态能力被切成两种：

- **一次性视觉请求** —— 当前、历史、取回画面和 mixed 视觉问题都由主 Agent 调 `query_multimodal` 交给 QueryWorker。QueryWorker 读取提问时刻的近期帧，再决定直接作答、召回历史记忆、检索外部资料或组合使用。
- **持续监控 / 深度研究** —— `set_monitor`（等某事件出现→提醒）与 `set_live_watcher`（后台持续逐段深研）两个后台 Agent。

这些能力的背后，是共享同一份 `FrameBuffer` + `MemoryStore` 的多个专职角色（见 [agent/multimodal/__init__.py](agent/multimodal/__init__.py)）。这个"一份感知、多方消费"的设计，是全系统的地基，我们会在每一章反复回到它。

## 为什么要分"看/听/想/说"四层？

如果不分层，会怎样？

最朴素的做法，是把每一帧画面、每一段音频，统统塞给一个大模型，让它一边看一边听一边想一边答。这在 demo 里能跑，在真实的连续场景里会立刻崩溃：

- **成本爆炸**：视频是 2fps 的连续流，一分钟就是 120 帧。每帧都喂给大模型，token 账单会让人心梗。
- **延迟灾难**：你问"屏幕上这个报错什么意思"，它却在慢慢消化过去十分钟的每一帧，半天答不上来。
- **注意力稀释**：真正重要的信息（你刚说的话、屏幕上刚弹出的错误）淹没在海量无变化的帧里。

分层，本质是**按"时间尺度"和"响应紧迫度"把工作拆开**：

| 层 | 关心的时间尺度 | 响应要求 | 典型角色 |
| --- | --- | --- | --- |
| **看** | 当下这一帧 / 最近几秒 | 实时 | FrameBuffer、场景去重、QueryWorker 提问时刻帧 |
| **听** | 当下这句话 / 最近几秒音频 | 实时（打断级） | 流式 ASR、本地意图、音视频对齐 |
| **想** | 从几秒到几小时 | 从秒级到分钟级 | 分层记忆、深度研究、事件监控 |
| **说** | 一句话的生命周期 | 实时（可被打断） | VoiceAgent、逐句 TTS、barge-in |

**"看"和"听"负责把连续的物理世界压缩成可消费的信号**——它们的核心矛盾是"信息量 vs 成本"，所以你会看到大量"去重、降采样、按场景动态调阈值"的设计。

**"想"负责在不同时间尺度上把信号变成知识和行动**——它的核心矛盾是"实时 vs 深度"，所以有了"主 Agent 负责语义路由，QueryWorker 负责一次性视觉问答，持续任务交给 Monitor/Watcher"的分工。

**"说"负责把知识变回自��的、有温度的、可被打断的人类对话**——它的核心矛盾是"流畅 vs 可中断"，所以有了逐句 TTS、强制门控、真打断这些设计。

## 数据流全景：一帧的一生

在钻进任何一层之前，先建立一张全局地图。想象一帧画面从摄像头进来，到系统对它做的所有事：

```
                        ┌─────────────────────────────────────────┐
   摄像头/屏幕/视频      │            前端 (React/tsx)               │
   麦克风              │  以固定 fps 采集帧 + PCM16 音频           │
        │              └───────────────────┬─────────────────────┘
        │                                  │  WebSocket (/api/ws)
        ▼                                  ▼
┌──────────────────────────────────────────────────────────────────┐
│                      hermes_glue (胶水层)                          │
│   _parse_and_dispatch: 大 payload 解析 dispatch 挪出事件循环线程   │
└───────┬──────────────────────────────────────────┬───────────────┘
        │ 画面帧                                    │ 音频帧
        ▼                                          ▼
┌───────────────────┐                    ┌────────────────────────┐
│  FrameBuffer      │◄── dHash 入口去重  │   流式 ASR (DashScope)  │
│  (2fps 环形缓冲    │    (SceneDhash     │   + 环境音 ASR          │
│   30min 窗口)     │     动态阈值)      │   + 本地 0.5B 意图      │
└─────┬─────────────┘                    └───────────┬────────────┘
      │  一份感知，多方消费
      ├──────────────┬──────────────┬───────────────┤
      ▼              ▼              ▼               ▼
┌──────────┐  ┌───────────┐  ┌───────────┐  ┌──────────────┐
│QueryWorker│  │ 分层记忆   │  │ Monitor   │  │   Watcher    │
│(提问时刻 │  │ Writer/    │  │ 原始短队列 │  │  持续稀疏流  │
│ 帧+召回)  │  │ Reviewer   │  │ 事件监控   │  │  深度研究    │
└──────────┘  └───────────┘  └───────────┘  └──────────────┘

用户问题 ──► 主 Agent（文本理解 + 语义路由）
                  ├─ query_multimodal ─► QueryWorker ─► 直接回复原消息
                  ├─ set_monitor ─► Monitor
                  └─ set_live_watcher ─► Watcher

麦克风 ─► 流式 ASR / VoiceAgent ─► 主 Agent 或语音快答 ─► TTS
```

这张图里藏着全书的四条主线：

1. **进来的那一刻**（看/听）：帧要不要留？音频里有没有人说话？—— 见第 1、2 章。
2. **一份感知怎么被多方消费**（架构）：FrameBuffer 和 MemoryStore 是所有人的共享内存 —— 贯穿全书。
3. **主 Agent 怎么按问题语义委派**（想）：一次性 QueryWorker 入口与持续 Monitor/Watcher 的边界 —— 见第 3 章。
4. **答案怎么变成有温度、可打断的声音**（说）：VoiceAgent 与 TTS 门控 —— 见第 4 章。

## 本书结构

- **第 1 章 · 看** —— 帧从哪来、FrameBuffer 怎么设计、场景感知的 dHash 动态去重、QueryWorker 提问时刻帧、watcher 逐段深研的 TTL+帧数双门。
- **第 2 章 · 听** —— 流式 ASR 的 WebSocket 协议、死 socket 自愈、麦克风生命周期、本地 0.5B 意图识别、barge-in、音视频时间基对齐。
- **第 3 章 · 想** —— 分层记忆（micro/macro/entity）、ReAct 深度研究、事件监控与 hook 主 Agent、系统提示的多模态编排、以及一堆真实踩过的坑。
- **第 4 章 · 说** —— VoiceAgent 的六次 LLM 调用、逐句 TTS 队列、对话模式统一门控、真打断、语音的"温暖化"改写。
- **第 5 章 · 贯穿全局的工程经验** —— 那些不属于任何单层、却决定系统能不能真正跑起来的教训：长会话性能、前后端状态一致性、配置架构、评测体系。

> **阅读建议：** 四个核心章节可以独立阅读，但强烈建议先读完这篇序章、再读第 1 章"看"——因为 FrameBuffer 这个共享地基，后面每一章都会用到。
